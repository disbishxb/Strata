# UI 开发与本地化规范

本文档规定本分支（fork）在 UI、本地化与架构方面应遵循的做法。

---

## 0. 元规则：本规范自身的修订

本节管的是这份文档怎么改。

- **允许只重写、不改内容。** 可以自由重写、重组、调整结构，前提是上一版传达的信息全部保留：任何一条规则都不能被删掉、削弱或悄悄抹去。
- **允许调整顺序。** 规则顺序、章节顺序、编号都可以改（比如把"允许修改底层"一节提到最前面），只要每条规则的含义和适用范围不变。
- **允许精简措辞。** 冗余、啰嗦的说法可以缩短或合并，但语义不能变。重写时如果产生了歧义，以旧版更具体的表述为准。
- **可追溯。** 对本文档的任何实质性重写、重排或措辞调整，都要写进提交信息（改了什么、为什么改），方便回溯意图。
- **信息完整优先于形式。** 结构调整和内容完整冲突时，以完整为准。绝不能为了排版好看而丢掉、合并掉或模糊任何一条现有规则。

### 0.1 提交信息
- 每条提交信息必须写明：本次提交的对象是用户（接收方是用户，而非协作者或上游）。

### 0.2 注释
- 注释一律用英文。
- 注释不允许写在“附近”：不得在被改代码行的邻近位置打注释。（例外：给用户演示修改处时。）
- 用脚本改文件时，不在受影响代码行上打注释。
- 注释一旦实际写进文件，必须是从整个文件视角看合理、稳定的注释，不能是阶段性的（即不能是相对上一次更新的说明，不能是变更记录式注释）。
- 由此：变更历史、原因、“改了什么”走提交信息；文件里的注释只承载对当前完整文件长期成立的内容（如不显而易见的行为、边界跨越），用英文写，不贴在改动行旁边。

### 0.3 文件可能被客户端截断
- 在 DeepSeek 安卓 App 等客户端内，过大的文件可能不会完整送达：AI 侧表现为内容被截断，用户侧提示“超出字数限制，DeepSeek 只阅读了前 XX%”。
- 无论阅读者是否为 DeepSeek，内容不完整都可能是客户端截断所致，而非文件本身如此。
- 因此：不得把截断后的末尾当作文件真实结尾；基于不完整内容做判断或修改前，应先确认是否被截断（如请用户分段贴出、用命令核对行数/字节数或尾部内容）。

## 1. 基础规则

### 1.1 布局位置
UI 元素必须放在语义上合理、符合预期的地方。
- 遵循 Android 和 Material Design 的标准布局惯例。
- 不要用让人困惑或不符合常规的方式嵌套元素。
- 新增 UI 属于语义上承载它的文件，而不是当下恰好打开的那个文件。

拿不准一段 UI 语义上该放哪时，问三个问题：
1. 如果把这个组件单独抽出来复用，它会被谁引用？引用方就是它的语义宿主。
2. 它的状态由谁的 ViewModel 持有？状态归属通常等于 UI 归属。
3. 删掉这个屏幕/组件时，这段 UI 应该跟着一起消失吗？如果是，它就不该住在别处。

> 举例：侧边栏的 UI 放在抽屉自己的文件（`StrataDrawer.kt`）里，而不是无关的屏幕文件（如 `SettingsScreen.kt`），即使两者相邻或耦合紧密。

### 1.2 本地化（i18n）
面向用户的字符串一律不得硬编码。
- 默认英文字符串放在 `app/src/main/res/values/strings*.xml`。
- 其他所有语言（`values-zh-rCN`、`values-ru`、`values-fa` 等）必须在同一次提交里一并更新。
- Compose 里用 `stringResource(R.string.xxx)`，非 Compose 环境用 `context.getString(R.string.xxx)`。

相关文件：
- 默认（英文）：`app/src/main/res/values/strings.xml`（以及 `strings_*.xml`）
- 中文：`app/src/main/res/values-zh-rCN/strings_*.xml`
- 俄文：`app/src/main/res/values-ru/strings_*.xml`
- 波斯文：`app/src/main/res/values-fa/strings_*.xml`
- 日文：`app/src/main/res/values-ja/strings_*.xml`

### 1.3 风格一致（本分支规则）
本项目是 fork：新增 UI 和功能必须与原项目的视觉风格、交互方式保持一致。
- 沿用现有的 Expressive Material 3 风格。
- 间距、形状（`RoundedCornerShape`）、排版、`MaterialTheme.colorScheme` 都要对齐。
- 不要引入破坏设计语言的通用或非标准 UI 组件。

相关文件：
- 主题与颜色：`app/src/main/java/dev/cluvex/strata/ui/theme/`
- 自定义表现力组件：`app/src/main/java/dev/cluvex/strata/ui/expressive/`

### 1.4 架构规范
保持关注点分离和标准项目结构。
- **前端（UI）：** Composable 保持纯粹，只负责渲染；状态管理、数据获取、业务逻辑放在 ViewModel 里。
- **后端（Core）：** 文件系统操作、解析、网络和重活放在 `app/src/main/java/dev/cluvex/strata/core/`。UI 文件里不放业务逻辑。
- **契约：** UI 只能通过 ViewModel 或已定义的 Repository 与 Core 交互。

相关文件：
- 状态/逻辑：`app/src/main/java/dev/cluvex/strata/feature/*/*ViewModel.kt`
- Core 后端：`app/src/main/java/dev/cluvex/strata/core/`

## 2. 修改底层

### 2.1 任何底层都可以改
因为这是 fork，只要实现、修复、打磨或重构功能需要，任何底层都可以改，包括但不限于：
- Core 后端：`app/src/main/java/dev/cluvex/strata/core/`（文件系统、解析、网络、APK、归档、DEX、PDF、加密、root/Shizuku、Termux 等）。
- 共享 UI 基础设施和可复用组件（如 `ZoneEditor.kt`、`SettingsComponents.kt`、`SettingsRepository.kt`、主题和表现力基础组件）。
- Repository、数据源、序列化模型、持久化配置结构。
- `native/` 下的原生代码，以及其他源集、模块或构建配置。

### 2.2 改底层时的约束
改的时候要注意：
- 尽量保持公共 API 和持久化设置的向后兼容。如果持久化格式必须变，要提供迁移或安全回退。
- 保持现有架构边界：重 I/O、解析、网络留在 `core/`；UI 留在 `feature/` 和 `ui/`。
- 不得绕过必要的校验、安全检查或签名验证。
- 不显而易见的行为要用注释写清楚（注释内容对当前完整文件长期成立，不是变更记录），并视情况更新相关 UI 规则、字符串和测试。变更历史与原因走提交信息。

### 2.3 相关规则的灵活处理
按 §2.1 改东西时，§1 的基础规则（尤其是 1.2、1.3、1.4）可以根据实际改动范围灵活处理：

- **1.2（i18n）：** 改动没引入新的用户可见字符串，就不用动字符串资源。改动修改或删除了现有用户可见文本，则要一致地更新所有受影响的语言（en / zh-rCN / ru / fa / ja）。不要为了"满足"规则而硬加字符串——只有改动真的产生了新 UI 才加。
- **1.3（风格）：** 重构共享 UI 基础设施（如 `ZoneEditor.kt`、`SettingsComponents.kt`）时，优先保证功能正确和交互一致。可见的风格偏差必须有具体的功能需求作依据。
- **1.4（架构）：** 改 core 或共享组件时，如果严格的 ViewModel/Repository 间接层会挡住必要的修复或重构，调整边界或直接调用是可以接受的。实际可行时仍优先沿用现有架构，并在注释里记录边界跨越。
- **可追溯：** 因 §2.1 改动而对 §1 产生的实质性偏差，必须记在提交信息里，方便追溯意图。
- **文档同步：** 按 §2.1 改动后，按 §4 维护文档。

## 3. 脚本化修改源码（可选方法论）

### 3.1 适用场景
用户提出 app 优化要求，且已知信息足够完整、修改内容足够清晰时，可以用脚本帮用户改源码。

只要是脚本即可——Python、Shell 或其他任何脚本语言都行，按需选用，不限制脚本语言或工具。

### 3.2 操作要点
任何语言的脚本（Python、Shell 等）都可以，按需选择。无论用哪种语言，都要注意：
1. **备份：** 统一放在 `~/build` 下，或项目同级目录。
2. **转义：** 注意 shell/正则/sed 等场景的转义问题，避免特殊字符被错误解释。
3. **贪婪：** 正则或批量替换时注意贪婪匹配，防止误伤超出目标范围的内容。
4. **import 完整性：** 改动后检查是否漏加 import（尤其是新增类型、Composable、工具类引用时）。

### 3.3 信息获取（可选）
脚本化修改所需信息不完整时，可以通过请用户贴出相关文件、或让用户执行命令并反馈结果来获取。
- 这是可选的获取信息手段，不是硬性要求。
- 不改变 §3.4 的定位：改动仍不清晰时，应先与用户确认再动手。

### 3.4 性质定位
以上均为**可选、非硬性要求**（属于方法论层面的提示），实际如何帮助用户可灵活处理。

### 3.5 与现有规则的关系
- 不覆盖 §1.2（i18n）、§1.3（风格）、§1.4（架构）等硬性约束；脚本改动若触及用户可见字符串、共享 UI 或 core 边界，仍按原规则处理。
- 属于 §2.1「任何底层都可以改」的操作手段之一；若因脚本改动产生对 §1 的实质性偏差，按 §2.3 的「可追溯」要求记录在提交信息中。
- 脚本语言不限，不强制某种语言。备份、转义、贪婪、import 检查属于操作安全建议，不是必须逐条满足的门槛；信息不完整或改动不清晰时，应先与用户确认再动手。

## 4. 代码改动后的文档同步

改源码后，按现有元规则文档维护文档，不在本文另立或复述规则：

- 路由文档：以 `docs/routing/zh-rCN/00-overview.md` 为准；改源码后更新对应分册引用的 byte 大小与职责。
- 变更记录：以 `docs/changes/zh-rCN/00-meta-rules.md` 为准。
- 两处文档为权威来源；本节仅作指引，冲突时以元规则文档为准。

### 4.1 changes 的两种情况
- **情况 A（跨版本更新内容）：** 改动属于相对上一发布版本的用户可见/开发者变化，按 `00-meta-rules.md` 归属写入 `01` 或 `02`，并写明是跨版本变化。
- **情况 B（单次未发布变更）：** 同一版本内发现并修掉的 bug、未发布的中间改动不单独记录；只修改“修好后仍不恰当”的内容，或把可以合并的内容综合起来叙述得更合理。
